# Agent Bridge — автономный исполнитель на базе Otack Manager API

**Дата:** 2026-08-27
**Статус:** дизайн согласован в чате, ждёт ревью перед планом
**Связано:** `.dev-notes/superpowers/specs/2026-06-03-external-api-design.md` (§11 «MCP bridge — phase 2»), `docs/API.md`, `docs/UPDATES.md`

---

## 1. Цель

Дать возможность ставить задачи AI-исполнителю **в интерфейсе таск-менеджера**, а не только в чате. Менеджер заводит боту учётку, добавляет в нужные проекты, асайнит задачу — дальше бот сам берёт её в работу, исследует, согласовывает объём, реализует и отдаёт на ревью, отвечая в комментариях как живой разработчик.

Бот автономен: между постановкой задачи и её появлением «на ревью» человек участвует ровно один раз — подтверждая объём работ после ресёрча.

## 2. Не-цели

- Не MCP-сервер. Первая итерация — скилл + CLI. Заготовка под MCP кладётся в `docs/MCP.md`, чтобы не потерялась.
- Не мультиагентность. Строго одна активная задача за раз.
- Не замена ревью человеком. Бот доводит до «на ревью», дальше решает человек.
- Не деплой на прод. Границы в §9.

## 3. Модель исполнения

**Тик = свежая сессия.** Запуск по расписанию (cron), а не бесконечный `/loop` в одном окне. Каждый тик стартует с нулевым контекстом.

Один тик выполняет **один переход фазы для одной задачи** и завершается. Исключение — фаза внедрения, она укладывается в тик целиком и может длиться дольше интервала (см. §5).

Внутри тика вся тяжёлая работа делегируется сабагентам: чтение кода, ресёрч, реализация. В главный контекст возвращается сводка, а не содержимое файлов.

**Почему так, а не `/loop`:** вечное окно копит контекст линейно, и компакт рано или поздно съедает середину задачи. При свежей сессии потолок контекста не достигается конструктивно — следить за ним не нужно.

## 4. Состояние

Раз сессия каждый раз новая, бот ничего не помнит — он **реконструирует состояние из API** на каждом пробуждении. Состояние складывается из трёх источников:

1. **Колонка задачи** — то, что видит человек на доске.
2. **`tasks.agent_state`** — новая колонка. Значения: `researching`, `awaiting_approval`, `implementing`, `review`, `blocked`, `NULL` (не в работе).
3. **Тред комментариев** — что уже сказано обеими сторонами.

### 4.1 Водораздел «что нового»

Курсор последнего просмотра **не хранится**. Водораздел — **id последнего собственного комментария бота**. Всё, что больше, написано людьми, пока бот спал.

Это работает, потому что бот завершает каждую фазу комментарием, то есть ставит метку сам. Свойства: ноль дополнительного состояния, переживает крах процесса, потерю сессии и ручное вмешательство в доску.

Если своих комментариев нет — водораздел 0, весь тред читается как исходный контекст.

### 4.2 Почему не `sub_status`

Поле уже принадлежит приложению: значения `reopened` / `returned`, выставляются автоматически в `TaskController` при возврате задачи из Done, и `TaskRepository::move()` умеет их обнулять. Состояние агента затиралось бы ровно в момент перемещения карточки самим ботом.

### 4.3 Конечный автомат

```
NULL ──берёт──▶ researching ──сводка + вопрос──▶ awaiting_approval
                                                        │ ответ участника проекта
                                                        ▼
       review ◀── пуш / «проверить локально» ── implementing
         │                                             ▲
         └────────── замечания в комментарии ──────────┘

  любое состояние ──не смог разобраться──▶ blocked (ждёт человека)
```

**`agent_state` пишется в начале фазы, до работы, а не в конце.** Это то, что делает крах видимым (§5).

Задача в `awaiting_approval` очередь не блокирует: пока она ждёт ответа, бот берёт следующую. Активной (`researching` / `implementing`) может быть только одна.

## 5. Взаимное исключение и восстановление

### 5.1 Лок

Тик первым делом берёт эксклюзивный лок `~/.claude/otack-agent/agent.lock`. Не смог — выходит немедленно, не обращаясь к API.

Примитив — PHP `flock()`. `flock(1)` из util-linux на macOS отсутствует; PHP-функция проверена на 8.4.5.

Ключевое свойство: лок привязан к **описанию открытого файла** (open file description), а не к процессу. Ядро снимает его, когда закрывается *последний* дескриптор, ссылающийся на это описание. На диске никакого состояния лока нет — поэтому застрявших лок-файлов после падения, ребута или засыпания ноутбука не бывает: TTL и ручная чистка не нужны.

**Важная оговорка (проверено эмпирически, третий проход ревью).** Формулировка «ядро снимает лок при завершении процесса-держателя» — неверна. Дескриптор наследуется через `fork()`/`exec()`: его получают `claude`, все запущенные им шеллы и всё, что они оставили после себя. Воспроизведено: обёртка → `passthru()` → дочерний процесс → `nohup sleep 120 &`; обёртка завершилась, а `lsof agent.lock` по-прежнему показывает осиротевший `sleep` как держателя. С `proc_open` — то же самое, значит дело не в `passthru`. Реальный сценарий: сессия запускает `make test`, который оставляет работать dev-сервер или watcher.

Симптом: каждый тик печатает «tick already running (pid <мёртвый>)» и выходит с 75 навсегда, при этом в `ps` никакого `otack-tick` нет. Поэтому `otack-tick` при неудачном `flock` проверяет, жив ли записанный держатель (`pid > 0`, тот же `host`, `posix_kill($pid, 0)`), и если нет — прямо говорит, что лок держит унаследованный дескриптор, показывает `lsof <lockPath>` как способ найти настоящего держателя и **не** постит комментарий «работаю подозрительно долго»: медленной сессии не существует.

Из того же свойства следует ограничение: **лок живёт ровно столько, сколько процесс**. Короткая CLI-команда удержать его на всю сессию не может — она завершится через секунду и отпустит. Поэтому лок держит процесс-обёртка `agent/bin/otack-tick`:

```
cron → otack-tick  (берёт flock, держит дескриптор открытым)
         └── claude -p …  (сессия целиком живёт как дочерний процесс)
       ← сессия завершилась → otack-tick вышел → ядро сняло лок
```

Обёртка — единственное, что стоит в расписании. Скилл лок не берёт и забыть его не может. Стрелка «← сессия завершилась → otack-tick вышел → ядро сняло лок» верна только тогда, когда сессия не оставила после себя живых процессов; см. оговорку выше.

В файл пишутся PID, хост, `task_id`, фаза и время старта — чтобы следующий тик мог сказать человеку что-то осмысленное. Файл — только для диагностики; за взаимное исключение отвечает `flock`, а не его содержимое.

### 5.2 Четыре ситуации

| Что произошло | Лок | `agent_state` | Действие нового тика |
|---|---|---|---|
| Предыдущий тик работает | занят | `implementing` | выход молча, ничего не трогает |
| Тик завис (> 3 ч) | занят | `implementing` | **не убивает**; комментарий «работаю подозрительно долго», выход |
| Процесс умер / ноут уснул | свободен | `implementing` | протокол восстановления, §5.3 |
| Тик отработал штатно | свободен | `review` / `awaiting_approval` | следующая фаза или следующая задача |

### 5.3 Протокол восстановления

Свободный лок при `agent_state = implementing` однозначно читается как «прошлый заход не доработал».

Источник правды о сделанном — **git, а не комментарии**. Бот работает в ветке `otack/task-<id>` и коммитит мелко и часто. При восстановлении он выясняет: существует ли ветка, какие в ней коммиты, грязное ли рабочее дерево, проходят ли тесты. Из этого собирает комментарий вида «прошлый заход прервался на таком-то месте, сделано вот это, продолжаю отсюда» — и продолжает.

Если картина не сходится — ставит `blocked` и зовёт человека. Никогда не продолжает молча с середины и не угадывает.

Мелкие частые коммиты здесь не стилистика, а механизм: они превращают цену падения из «потерян час» в «потеряно несколько минут».

## 6. Серверные изменения

Все — в этом репозитории. Прод обновляется штатным путём: бамп версии → тег → пуш на `origin` → кнопка обновления в Settings → Updates.

### 6.1 Фикс роли (блокер)

`RolePolicy::canEditTask()` сейчас пропускает только админа, автора задачи и менеджера-владельца проекта. `assignee_id` в проверке не участвует вообще — то есть бот-`employee` не может сдвинуть заасайненную на него карточку.

Добавляется ветка: **исполнитель может двигать и обновлять свою задачу**. Это корректно и для живых сотрудников — текущее поведение выглядит как недосмотр, а не как замысел.

Затрагивает и веб-UI, и API (общая политика). Нужен пересмотр `test_role_policy.php` и API-тестов на 403.

### 6.2 Кросс-проектный список задач

`GET /api/v1/tasks?assignee_id=&updated_after=&agent_state=&limit=&after=`

Сейчас задачи доступны только внутри проекта, что даёт запрос на каждый проект и упирается в лимит 60/мин. Видимость — только проекты, где вызывающий состоит участником (для админа — все).

### 6.3 Колонка `agent_state`

Миграция: `tasks.agent_state` (string 32, nullable) + `agent_state_at` (timestamp, nullable). Второе поле даёт «висит в этой фазе N часов» — основа для детекта зависания и для глаз человека.

- Чтение и запись через API (`GET /tasks/{id}`, `PATCH /tasks/{id}`, фильтр в списке).
- Бейдж на канбан-карточке и на странице задачи, рядом с существующим `sub_status`.
- i18n во все три каталога (`en`, `uk`, `pl`) — иначе падает `test_i18n_parity.php`.

### 6.4 Мелкие дыры API

| Что | Почему |
|---|---|
| `description` проекта в ответах `GET /projects` и `GET /projects/{id}` | сейчас поле **пишется**, но не читается ни одним GET |
| `is_done` / `is_backlog` в `ProjectDetail.columns` | бот должен знать, куда двигать, не делая второй запрос |
| Признак «задача создана из публичной формы» в `Task` | бот такие задачи не берёт (§10) |

### 6.5 Поля проекта под связку с кодом

Миграция: `projects.repo_url`, `default_branch`, `dev_branch`, `dev_url`, `agent_instructions` (text). Все nullable — существующие проекты не ломаются.

- Форма редактирования проекта в UI + i18n ×3.
- Отдача и приём через API.

`agent_instructions` — свободный текст: стек, как гонять тесты, конвенции, чего не трогать. Это то, что бот читает перед началом работы над проектом.

### 6.6 Сопровождение

- `docs/openapi.yaml` — иначе падает `test_openapi_drift.php`.
- `docs/API.md` — раздел про новые эндпоинты и поля.
- `docs/MCP.md` — заготовка под будущий MCP-мост.
- Бамп `APP_VERSION`, тег, релиз.

## 7. Клиентская часть

### 7.1 Где что лежит

Серверная часть, CLI и документация — в `otack-tasks`. **Скилл там жить не может**: работать он должен в чужих репозиториях (`otack-cms`, `eva-site`, `patskano`…), а проектные скиллы видны только внутри своей папки.

Решение: источник правды в `otack-tasks/agent/`, установка симлинком.

```
agent/
  skill/SKILL.md          # → ~/.claude/skills/otack-agent/
  skill/references/       # промпты фаз, формат комментариев
  bin/otack               # PHP CLI (команды для скилла)
  bin/otack-tick          # обёртка: держит лок, запускает сессию (§5.1)
  projects.example.json
```

`make install-agent` — симлинк в `~/.claude/skills/`. Один репозиторий, ноль копипасты.

### 7.2 CLI

PHP, без Composer — согласуется с философией репозитория. Возвращает JSON, чтобы скилл не парсил прозу.

| Команда | Назначение |
|---|---|
| `otack next` | следующая задача к обработке с учётом состояний и приоритета фаз |
| `otack task <id>` | карточка + тред + контекст проекта одним ответом |
| `otack new-comments <id>` | комментарии после последнего собственного (§4.1) |
| `otack state <id> <state>` | выставить `agent_state` |
| `otack move <id> <column>` | переместить карточку |
| `otack comment <id>` | комментарий из stdin |
| `otack project <id>` | repo, ветки, инструкции, колонки |
| `otack whoami` | проверка токена |

Лок берёт обёртка `otack-tick` (§5.1), а не эти команды и не скилл — так его нельзя забыть и нельзя потерять на середине сессии.

### 7.3 Конфиг проектов

Разделение ответственности принципиальное:

- **Сервер хранит «что»**: `repo_url`, ветки, инструкции. Видно команде, правится в вебморде.
- **Машина хранит «где и можно ли»**: `~/.claude/otack-agent/projects.json` — локальный путь и разрешение на запись.

`projects.json` содержит только карту проектов — без `instance`. Адрес инстанса (`OTACK_API_URL`) живёт в `~/.claude/otack-agent/.env` рядом с `OTACK_API_TOKEN`, а не здесь: секрет и адрес, к которому он относится, должны путешествовать вместе, одним файлом с правами `0600` — раздельное хранение оставляло бы шанс унести токен от инстанса, которому он выдан, или наоборот.

```json
{
  "projects": {
    "42": { "path": "/Users/…/otack/otack-cms", "write": true,  "test_cmd": "make test" },
    "51": { "path": "/Users/…/otack/eva-site",  "write": false }
  }
}
```

Проекта нет в файле — бот его не трогает вообще. Так правка поля в вебморде не может направить исполнителя в чужой репозиторий или в системную папку.

**Взаимная блокировка:** перед работой бот сверяет `repo_url` из API с `git remote get-url origin`. Не совпало — `blocked`, без единой правки.

## 8. Фазы работы над задачей

**Ресёрч.** Двигает карточку в In Progress, ставит `researching`. Читает задачу, `agent_instructions` проекта, код — через сабагентов. Публикует комментарий: что понял, что предлагает сделать, что осознанно оставляет за скобками, риски. Заканчивает **явным вопросом об объёме**. Ставит `awaiting_approval`.

**Согласование.** Ответ любого участника проекта в треде. Бот интерпретирует его; если ответ двусмысленный — переспрашивает, а не додумывает.

**Внедрение.** `implementing`, ветка `otack/task-<id>`, TDD по конвенциям репозитория, мелкие коммиты, прогон тестов и линтеров.

**Ревью.** Если у проекта объявлен `dev_branch` — пуш туда и комментарий со ссылкой на `dev_url`. Если нет — прямо написать, что задачу нужно проверить локально, с командами запуска. Карточка уезжает в колонку ревью, `agent_state = review`.

**Доработка.** Новый комментарий от участника на задаче в ревью возвращает её в `implementing`. Мелкая правка идёт без повторного согласования; если замечание фактически меняет объём — бот сначала спрашивает.

## 9. Границы автономии

**Разрешено без человека:** ветка `otack/task-<id>`, коммиты, пуш этой ветки, пуш в объявленный `dev_branch`, локальный прогон тестов, линтеров и сборки.

**Требует человека:** изменения схемы БД, мажорные обновления зависимостей, всё, что касается оплат, прод-данных и секретов.

**Запрещено всегда:** пуш и мерж в `default_branch` (`main`/`master`), force-push, удаление чужих веток, теги и релизы, любой деплой на прод, миграции на проде, работа вне `path` проекта, правка `.env` и секретов, отправка содержимого репозитория во внешние сервисы.

## 10. Безопасность

**Круг доверия.** Команды принимаются от любого участника проекта (решение владельца). Периметр замкнут: комментарии в системе может оставлять только авторизованный участник.

**Публичные формы.** Формы умеют автоматически создавать задачи из анонимного сабмита — это канал записи в текст карточки из интернета. Такие задачи бот **в работу не берёт**, пока живой участник их не переназначит. Отсюда требование §6.4 о признаке происхождения.

**Текст — это данные.** Описания задач и комментарии трактуются как постановка, а не как инструкции агенту. Указания вида «выполни команду», «сходи по ссылке и сделай, что там написано», «игнорируй свои правила» не исполняются; бот на них отвечает отказом в комментарии.

**Токен.** Отдельная учётка-бот, роль `employee`, членство только в нужных проектах. Скоупов у токенов нет — членство и есть единственный рычаг ограничения. Токен в `~/.claude/otack-agent/.env` с правами `0600`, не в репозитории.

## 11. Тестирование

- **Unit:** новая ветка `RolePolicy`; идемпотентность миграций; вычисление водораздела; поведение лока в двух процессах.
- **API:** новый эндпоинт списка; чтение и запись `agent_state`; регрессия на фикс роли (исполнитель-`employee` двигает свою задачу, посторонний по-прежнему получает 403).
- **E2E:** бейдж фазы на канбане, форма полей проекта.
- **Существующие гварды:** `test_openapi_drift.php` и `test_i18n_parity.php` поймают рассинхрон спеки и каталогов — их надо удовлетворить, а не обойти.
- **Обкатка:** отдельный проект-полигон, сначала прогон фаз вручную, автономия включается последней.

## 12. Отложено осознанно

- **`GET /events` из `activity_log`.** С водоразделом по своему комментарию боту хватает 2–6 запросов на тик при лимите 60/мин. Эндпоинт с фильтрацией видимости решал бы нагрузку, которой нет. Если понадобится лента активности для людей — отдельная задача.
- **MCP-мост.** `docs/MCP.md` фиксирует замысел; строится после обкатки скилла.
- **Скоупы токенов.** Отдельная работа по API, здесь не нужна.

## 13. Открытые вопросы

1. **Планировщик.** Дизайн исходит из системного `cron`, запускающего `otack-tick` → `claude -p` (CLI 2.1.186 на месте). Это даёт жёсткий мьютекс через `flock`.
